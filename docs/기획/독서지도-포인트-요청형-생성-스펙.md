# 독서지도 포인트 요청형 생성 스펙

상태: 구현 기준안 · 2026-10-05
관련 아이디어: [목차퀴즈-사상-연결-독서지도.md](목차퀴즈-사상-연결-독서지도.md)

## 결정

사용자가 퀴즈 첫 풀이로 포인트를 얻고, **`지도 만들기` 또는 `지도 갱신하기`를 직접 눌러 포인트를 사용**한다. 서버는 그 요청에서만 본인의 풀이 데이터를 모아 AI로 의미 관계를 생성한다. 지도 열람과 퀴즈 제출 때 AI를 호출하지 않는다. 만들어진 지도는 저장해 다시 보여준다.

모든 퀴즈 쌍을 사전 비교·저장하는 방식은 사용하지 않는다. 사용자 요청이 들어올 때도 입력 퀴즈 수와 출력 선 수를 제한한다. DB에서 더 큰 위험은 전체 퀴즈 쌍보다 동시 요청의 중복 차감, 장시간 AI 호출 중 트랜잭션 점유, 실패 후 미환급이다. 각 단계가 짧은 DB 트랜잭션으로 끝나도록 한다.

퀴즈 생성 시 관계 태그를 필수로 만들지 않는다. 태그가 겹치지 않는 보완·대조 관계도 있으므로 태그 일치만으로 선을 확정하지 않는다. 초기 버전은 요청당 최대 40개 퀴즈를 AI에 한 번 전달하고, 결과로 검증된 선만 저장한다. 입력 40개의 가능한 쌍 780개를 DB 행이나 AI 호출 780회로 만들지 않는다. 데이터가 커져 한 번의 입력으로 부족해질 때만 태그·임베딩을 후보 검색용으로 검토한다.

```text
첫 풀이(+10P) → 지도 화면에서 잔액·분석 가능 퀴즈 수 확인
              → 지도 만들기(20P) / 새 풀이 후 지도 갱신하기(10P)
              → 포인트 예약·작업 생성 → 비동기 AI 분석
              → 성공: 지도 저장·예약 확정 / 실패: 전액 환급
```

포인트 금액은 첫 출시의 제안 값이다. 서버의 한 정책 위치에서 관리하고 앱은 API의 `cost`를 표시한다. 운영 데이터로 완료율과 AI 비용을 본 뒤 조정한다. 과거 풀이에도 같은 적립률을 적용한다.

## 사용자 경험과 상태

| 상황 | 화면 |
| --- | --- |
| 지도 없음, 첫 풀이 2개 미만 | 현재 책→목차→퀴즈 지도와 `퀴즈를 2개 이상 풀면 생각 연결을 만들 수 있어요` 표시. 생성 버튼 비활성 |
| 지도 없음, 포인트 부족 | 현재 지도·잔액·필요 포인트를 보여줌. 퀴즈로 포인트 얻기 이동 |
| 생성 가능 | `지도 만들기 · 20P` 버튼과 분석 범위(최근 최대 40개 첫 풀이)를 표시. 누르기 전 차감과 실패 환급을 확인할 수 있음 |
| 생성 중 | 버튼 비활성, `생각을 연결하고 있어요` 상태. 앱을 나갔다 돌아와도 작업 상태 복원 |
| 생성 완료 | 기존 책→목차→퀴즈 지도에 의미 관계선을 더하고, 화면 아래에 관계 유형·이유가 있는 큰 카드 표시. 관계가 없는 점은 그대로 둠 |
| 새 퀴즈 풀이 후 | 기존 지도는 계속 보이고 `새로운 생각이 있어요. 지도 갱신하기 · 10P` 표시 |
| AI 실패 | 기존 지도를 유지하고 예약 포인트 전액 환급. 같은 버튼으로 다시 시도할 수 있음 |
| 유효한 관계 0개 | 기존 관계선과 포인트를 유지하고 이번 풀이 집합을 분석 완료로 기록. 새 퀴즈를 푼 뒤 다시 갱신 가능 |

사용자가 선을 직접 그리거나 작은 선을 정확히 탭할 필요가 없도록 **관계 카드**를 기본 탐색 수단으로 둔다. 요청 버튼은 사용자가 AI 비용을 쓸지 결정하는 조작이며, 선의 의미를 임의로 정하는 조작이 아니다. 관계 설명에는 정답·해설에 있는 내용만 쓴다. 원문 근거가 없으면 “책의 확정된 사상”으로 표현하지 않는다.

## 포인트 규칙

- 첫 답 제출이 성공할 때, 정오와 관계없이 고유 `(memberId, quizId)`당 `+10P`를 한 번 적립한다. 기존 `/api/v3/learning/quizzes/{quizId}/submit`과 레거시 첫 풀이 경로를 모두 포함하고 복습 제출은 제외한다. 첫 제출 저장과 적립 원장 기록은 같은 트랜잭션에서 처리한다.
- 출시 전 풀이 기록도 고유 `(memberId, quizId)`당 `+10P`로 **한 번 백필**한다. 백필 스크립트 재실행과 재전송에도 중복 적립하지 않도록 원장 유니크 키를 사용한다. 퀴즈 삭제가 과거 적립액을 소급 차감하지 않는다.
- 지도 만들기 `20P`, 갱신 `10P`. 같은 풀이 집합이면 갱신할 수 없고, 갱신에는 새 첫 풀이가 1개 이상 필요하다. 이미 처리 중인 작업이 있으면 새 요청은 `409`로 거절한다. 동일 `requestId` 재전송에는 기존 작업을 돌려준다.
- 요청 시 잔액을 잠그고 비용을 **예약 차감**한다. 성공적으로 검증된 관계가 1개 이상 저장됐을 때 소비가 확정된다. AI 오류·시간초과·유효 관계 0개에는 동일 작업 ID로 환급 원장을 한 번 기록한다. 재시도·중복 콜백은 추가 차감·환급을 만들지 않는다.
- 포인트는 현재 독서지도 생성·갱신에만 사용한다. 현금 가치, 외부 결제, 양도, 일반 상점 기능은 이 범위에 없다.

## AI 입력과 결과

- 서버가 로그인 사용자의 **최초 풀이 시점 기준 최근 최대 40개 고유 퀴즈**를 직접 조회한다. 복습은 입력 순서나 갱신 조건을 바꾸지 않는다. 입력에는 책·목차 제목, 질문, 정답 선택지와 정답 해설만 담는다. 오답을 저자의 주장으로 사용하지 않는다. 클라이언트가 보낸 퀴즈 ID나 정답 텍스트는 AI 입력의 신뢰 근거로 쓰지 않는다.
- 첫 생성과 갱신 모두 최근 40개를 분석한다. 갱신은 이 집합에 속한 쌍의 기존 관계를 새 결과로 교체하고, 범위 밖 오래된 관계는 최대 저장 한도 내에서 유지한다. 기존 지도 이후 새로 푼 퀴즈가 최소 1개 있어야 갱신할 수 있다.
- AI는 최대 20개 관계를 구조화된 JSON으로 반환한다. 각 관계는 `fromQuizId`, `toQuizId`, `type`(`SAME_CONCEPT`, `COMPLEMENTS`, `CONTRASTS`, `PREREQUISITE`), `reason`, 양쪽의 근거 요지를 갖는다. 찾지 못하면 빈 배열을 반환한다.
- 서버는 두 ID가 요청 스냅샷에 있고 서로 다르며, 타입과 설명·근거가 비어 있지 않고, 중복·자기 연결이 아니며, 둘 다 현재 유효한 퀴즈인지 검사한다. 검증되지 않은 항목은 버린다. 연결 수를 채우려고 근거 없는 선을 만들지 않는다.
- 프롬프트는 각 입력을 원문이 아닌 **퀴즈 데이터**라고 명시한다. 근거 없는 책 내용, 페이지, 인용을 생성하지 못하게 한다. 작업에는 입력 퀴즈 ID 목록과 실행·완료 시각을 남긴다. 모델 버전 기록은 운영 추적 개선 항목이다.

## 데이터 모델과 트랜잭션

| 저장 대상 | 핵심 필드·제약 |
| --- | --- |
| `reading_point_wallet` | `member_id` 유니크, `balance >= 0` |
| `reading_point_ledger` | `member_id`, `kind`(`QUIZ_EARN`, `MAP_RESERVE`, `MAP_REFUND`), `reference_id`, `delta`, `created_at`; `(member_id, kind, reference_id)` 유니크 |
| `reading_map_job` | `id`, `member_id`, `request_id`, `mode`, `status`, `cost`, `source_quiz_ids`, `latest_attempt_id`, `started_at`, `finished_at`; `(member_id, request_id)` 유니크 |
| `reading_map` | `member_id` 유니크, `version`, `last_job_id`, `last_attempt_id`, `analyzed_quiz_count`, `updated_date` |
| `reading_map_link` | `member_id`, 양쪽 `quiz_id`, 관계 유형, 방향, 설명, 양쪽 근거 구절, 생성 작업 ID; 사용자별 정렬된 ID 쌍 유니크 |

작업 상태는 `QUEUED → RUNNING → SUCCEEDED | NO_LINK | FAILED`로만 전이한다. 요청 트랜잭션은 회원·지갑을 잠그고 입력 적격성·잔액·중복 요청을 확인한 뒤 차감 원장과 작업을 함께 저장한다. AI 호출은 **DB 트랜잭션 밖**에서 수행한다. 완료 트랜잭션은 작업행을 잠그고 상태를 단 한 번 전이시키며, 성공이면 지도·선을 교체 또는 병합하고, 실패·무관계면 환급한다. 서버 재시작으로 오래 멈춘 작업은 만료 처리 후 환급한다. 완료된 작업을 재처리해도 지도 버전과 잔액이 다시 바뀌지 않는다.

지도 읽기는 저장된 스냅샷과 현재 유효한 퀴즈의 교집합만 반환한다. 퀴즈 삭제 시 관계선을 무효화하되 포인트 적립·사용 내역은 보존한다. 회원 탈퇴 시 지도·작업·원장·지갑을 기존 회원 데이터 삭제 순서에 맞춰 제거한다. 저장 관계는 해당 사용자에게만 공개한다.

## API 계약 초안

모두 로그인 필수, 기존 `ResponseForm` 응답 래퍼를 사용한다.

| 메서드·경로 | 목적 | 주요 응답 |
| --- | --- | --- |
| `GET /api/v3/learning/me/reading-map` | 잔액·가격·작업 상태·저장 지도·관계·갱신 가능 여부 | `balance`, `createCost`, `refreshCost`, `answeredQuizCount`, `analyzedQuizCount`, `hasNewQuizzes`, `status`, `jobId`, `links`, `version` |
| `POST /api/v3/learning/me/reading-map/jobs` | 생성·갱신 요청. `requestId` UUID, `mode=CREATE|REFRESH` | `jobId`, `status=QUEUED`, `balance`, `reservedCost` |
| `GET /api/v3/learning/me/reading-map/jobs/{jobId}` | 진행·완료 상태 확인 | `jobId`, `status`, `balance`, `reservedCost`, `errorCode` |

같은 `requestId`·같은 본문 재전송은 이전 결과를 반환한다. 같은 `requestId`에 다른 모드·입력을 보내면 `409`. 잔액 부족, 풀이 수 부족, 새 풀이 없음, 이미 작업 중은 구별되는 4xx 코드로 반환한다. 작업 실패는 상태 조회에서 표시하고 환급 결과를 함께 준다. 클라이언트는 실행 중 2~3초 간격으로 폴링하다 화면 이탈 시 멈추며, 재진입 시 `GET` 상태를 다시 읽는다.

## 부하 상한과 검증

- 생성·갱신 요청 외 AI 호출 없음. 사용자당 활성 작업 1개. 입력 최대 40개, 출력 최대 20개 선, 저장 최대 100개 선, 요청당 AI 호출 1회다. 프로세스당 AI 동시 실행을 2개로 제한하고 10분 이상 실행 중인 작업은 만료·환급한다. 조회는 사용자 인덱스로 범위를 좁히고 퀴즈·정답을 일괄 조회해 N+1을 막는다. 서버 인스턴스가 늘면 전역 동시성 제한이 별도로 필요하다.
- 성공한 지도는 GET에서 AI 재호출 없이 읽는다. 새 퀴즈가 생겨도 기존 관계는 자동으로 다시 분석하지 않는다.
- 검증: 첫 풀이 중복·복습·레거시 경로의 적립, 백필 재실행, 잔액 경계, 동시 생성 요청, 동일 requestId 재전송, AI 실패/0개/시간초과 환급, 완료 콜백 중복, 앱 재시작 후 작업 복원, 삭제된 퀴즈 관계 필터를 확인한다.
- 품질: 표본에서 관계 유형·근거를 평가한다. 실제 책 원문이 없는 경우 연결 설명은 퀴즈의 정답·해설을 벗어나지 않아야 한다.

## 구현 순서

1. 기존 기획의 사전 생성 가정을 이 스펙으로 대체하고, 포인트 지갑·원장·백필 SQL·첫 풀이 적립을 구현한다.
2. 작업 선점·환급·만료 복구와 AI 입력/검증·지도 저장을 서버에 구현하고 API를 검증한다.
3. 앱에 잔액, 생성·갱신 버튼, 실행 상태, 저장된 관계 카드와 선을 연결한다.
4. 실패·동시성·마이그레이션 검증 후 현재 코드와 스펙을 맞춘다.
