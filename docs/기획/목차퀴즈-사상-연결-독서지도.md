# 목차퀴즈의 생각을 연결하는 독서지도

> 이 문서는 초기 아이디어 기록이다. 사전 관계 생성·자동 공개·연결 보너스와 관련된 구현 결정은 [독서지도 포인트 요청형 생성 스펙](독서지도-포인트-요청형-생성-스펙.md)으로 대체되었다.

## 한 줄 제안

독서지도의 기본 단위를 `책 → 목차 → 푼 퀴즈`에서 끝내지 않고, **퀴즈가 되짚는 주장·개념과 그 사이의 관계**까지 확장한다. 연결은 서비스가 자동으로 만들고, 사용자는 카드에서 “두 생각이 왜 연결되는지”를 읽고 양쪽 목차의 퀴즈를 다시 풀 수 있다.

## 지금 상태와 문제

- 현재 지도는 복습 목록의 `bookId`, `chapterId`, `quizId`, 질문을 모아 책→목차→문제 노드를 만들고 부모·자식 선을 그린다. 화면에는 책별 목차와 질문을 보여주지만, 목차 사이 또는 책 사이의 의미 관계는 없다.
- 서버에는 목차당 최대 한 문제와 정답 선택지·해설이 있다. 다만 복습 목록과 현재 지도 데이터에는 **정답·해설이 포함되지 않는다**. 연결 분석은 서버 내부의 퀴즈 데이터에서 수행해야 한다.
- 현행 생성 지침은 확인 가능한 목차별 핵심 개념을 우선하며, 책 제목과 목차만 보고 내용을 추측하지 말도록 한다. 따라서 “모든 정답이 책 전체를 관통하는 사상”이라고 일괄 간주할 수 없다. 어떤 문제는 한 목차의 개념이나 구분만 다룰 수 있다.

기획의 핵심은 선의 개수가 아니라 **연결의 설명 가능성**이다. 같은 단어가 들어간 퀴즈 둘을 잇는 것만으로는 독자가 책의 내용을 더 잘 기억하지 못한다.

## 사용자가 얻게 될 경험

1. 목차 퀴즈의 첫 답을 제출하면 해설 화면과 함께 해당 점이 지도에 생기고 기본 포인트를 받는다. 원래의 책→목차→퀴즈 계층은 그대로 탐색할 수 있다.
2. 의미 관계가 미리 확인된 퀴즈 두 개를 모두 풀면 서비스가 두 점 사이의 선을 자동으로 밝히고 연결 발견을 알려준다. 화면에는 대표 관계를 **큰 카드**로 먼저 보여주고, 지도는 그 위치를 확인하는 보조 시각화로 쓴다.
3. 카드에는 **관계 유형 + 한 문장 이유 + 양쪽의 질문·정답 요지 + 목차**가 나온다. “왜 연결됐지?”에 답할 수 있어야 한다. 카드를 누르면 해당 목차나 퀴즈로 이동한다.
4. 사용자는 양쪽 퀴즈를 다시 풀 수 있다. 관계가 틀렸을 때만 카드의 “연결이 어색해요”를 한 번 눌러 알릴 수 있다. 직접 노드나 선을 만들고 끌어 놓는 조작은 제공하지 않는다.

모바일 화면에서 가는 선을 정확히 탭하거나 노드를 끌어 연결하는 조작은 핵심 경험으로 삼지 않는다. 사용자가 해야 할 일은 **읽고, 퀴즈를 풀고, 발견된 연결을 살펴보는 것**이다. 피드백도 선택 사항이다.

### 풀이 → 포인트 → 연결 발견

**관계의 존재와 사용자의 발견을 분리한다.** 서버는 퀴즈 내용으로 `A와 B가 연결되는가`를 미리 판정한다. 개인 지도는 사용자가 A와 B의 첫 답을 제출한 시점에 그 관계를 드러낸다. 현재 풀이 API에는 별도의 해설 열람 기록이 없으므로 첫 제출을 활성화 기준으로 삼고, 결과 화면에서 해설과 연결 이유를 함께 보여준다. 포인트가 쌓였다는 이유로 관계 없는 두 점을 연결하거나, 포인트를 써서 선을 사는 방식은 쓰지 않는다.

| 사용자 행동 | 지도와 보상 |
| --- | --- |
| 퀴즈 A 첫 답 제출 | A 점 활성화, 기본 포인트 최초 1회 지급 |
| A와 연결 가능한 퀴즈 B가 아직 미완료 | 선은 숨기고, 원한다면 B의 책·목차로 이동하는 다음 읽기 카드를 제안. 정답과 관계 이유는 미리 공개하지 않음 |
| 퀴즈 B 첫 답 제출 | B 점 활성화, 이미 검증된 `A—B` 관계를 자동 공개하고 연결 발견 보너스 최초 1회 지급 |
| 새로 푼 퀴즈에 검증된 관계가 없음 | 점과 기본 포인트만 남음. 화면을 채우기 위한 선은 만들지 않음 |

복습을 반복해도 같은 퀴즈·관계의 포인트는 다시 지급하지 않는다. 정답 여부와 관계없이 첫 제출을 인정하고 해설을 곧바로 보여준다. 한 문제로 여러 관계가 동시에 열려도 보너스는 상한을 둔다. 포인트 총량보다 “이번에 어떤 생각이 연결됐는지”가 주된 피드백이 되도록 한다. 점·선 활성화와 보상 지급은 서버에서 멱등하게 처리한다.

예시(실제 책·퀴즈 데이터가 아닌 설명용):

> A: “습관을 바꾸려면 실행할 행동을 작게 정한다.”
> B: “반복을 늘리려면 시작할 때의 마찰을 낮춘다.”
> 관계: **상호보완** — 행동의 크기를 줄이면 시작 비용도 낮아진다는 공통 기제가 있다.

반대로 “성공”이라는 단어만 공유하거나, 두 주장에 찬반 방향이 다른데도 유사하다는 이유로 연결해서는 안 된다.

## 무엇을 연결할까

지도에서 실제로 연결하는 대상은 **푼 퀴즈에서 추출한 하나의 검증 가능한 주장 또는 개념**이다. 책과 목차는 그 생각의 출처와 탐색 경로로 유지한다. 하나의 퀴즈가 여러 생각을 담으면 우선 대표 주장 하나만 추출하고, 분리할 수 없으면 연결 대상에서 제외한다.

각 생각은 다음을 가진다.

| 필드 | 의미 |
| --- | --- |
| `quizId`, `chapterId`, `bookId`, `quizRevision` | 원본과 생성·수정 버전 식별 |
| `claim` | 정답과 해설을 바탕으로 쓴 짧은 주장·개념 문장 |
| `conceptTags` | 이 퀴즈의 구체적인 개념 1~3개. 검색용 후보이며 관계의 증거는 아님 |
| `scope` | 해당 목차에만 해당하는지, 여러 목차에 걸쳐 확인됐는지 |
| `evidenceLevel` | `QUESTION_ONLY`, `ANSWER_EXPLANATION`, `VERIFIED_SOURCE` 등 근거 수준 |
| `sourceRef` | 확인 가능한 자료가 있을 때만 저장하는 근거 위치·출처 |
| `status` | 자동 공개, 비공개 후보, 숨김 등 품질 상태 |

`QUESTION_ONLY`는 후보 탐색에만 쓰고 사용자에게 “저자의 주장”으로 표시하지 않는다. 정답 선택지와 해설이 있어도 그것이 곧 원문 검증을 뜻하지 않는다. 실제 출처를 확보한 경우에만 “책에서 확인된 주장” 같은 표현을 쓸 수 있다. 그 외에는 “이 퀴즈가 다루는 생각”이라고 표현한다.

관계는 최소한 **같은 개념**, **상호보완**, **원인·결과**, **전제·적용**, **대조**로 나눈다. `원인·결과`, `전제·적용`은 방향을 저장한다. 의미가 비슷하다는 이유만으로 상호보완이나 인과관계를 만들지 않는다. 관계를 설명할 근거가 없으면 선을 만들지 않는다.

### 퀴즈 생성 시 태그를 함께 만들까?

**만든다. 다만 태그가 겹친다는 이유만으로 선을 확정하지는 않는다.** 퀴즈를 생성·저장할 때 질문, 정답, 해설에서 `claim`과 구체적인 `conceptTags`를 함께 추출하면 이후 후보를 찾는 비용을 줄일 수 있다. 태그 추출 실패가 퀴즈 생성 실패로 이어지지 않도록 메타데이터는 별도 재처리할 수 있게 한다. 책 제목·목차만 보고 태그를 붙이지 않는다.

생성 모델이 쓴 표현은 그대로 비교하지 않고 책 전체 퀴즈가 저장된 뒤 정규화한다. 예를 들어 `시작 장벽`, `행동 마찰`, `실행 저항`을 같은 개념으로 묶을 수 있는지 검토하고, `성공`, `삶`, `변화`처럼 너무 넓은 태그는 연결 후보에서 제외한다. 처음에는 소수의 표준 태그와 동의어 사전으로 시작하고, 새 태그는 검토 후 편입한다.

태그 일치만 쓰면 다음을 놓친다.

- **다른 개념의 상호보완:** `작은 행동`과 `실행 마찰 낮추기`는 태그가 달라도 서로를 설명할 수 있다.
- **같은 주제에 대한 반대 주장:** 둘 다 `동기부여` 태그여도 한쪽은 외적 보상을, 다른 쪽은 내적 동기를 강조할 수 있다. 단순 연결은 차이를 지운다.
- **책의 큰 흐름:** 목차별 퀴즈가 `문제 → 원인 → 해결`을 나눠 다룬다면 동일 태그가 없어도 함께 봐야 의미가 생긴다.

그래서 태그는 **후보 검색의 첫 관문**으로 쓰고, 후보 쌍의 `claim`·정답 해설을 비교해 관계 유형과 한 문장 이유를 정한다. 추가로 한 권의 검증된 퀴즈들을 모아 책 전체에서 반복되는 주제 1~3개를 요약하고, 각 주장에 해당 주제와의 소속 여부를 붙이는 방안을 검토한다. 이 주제는 여러 목차를 묶어 보여주는 탐색 기준이다. 원문 근거가 없다면 “책의 확정된 핵심 사상”으로 단정하지 않는다.

**첫 버전의 단순한 규칙:** 표준 태그가 겹치고 양쪽 주장도 같은 개념을 다룬다고 자동 판정된 경우에만 `같은 개념` 관계를 만든다. 태그가 달라도 관계가 있을 만한 쌍은 AI가 제안하되 공개 기준을 더 엄격하게 둔다. 지도에는 같은 태그의 모든 쌍을 잇지 않고 주제별 대표 관계만 보여준다.

## 연결 방법: 기계적 후보 찾기 + AI 판정

| 단계 | 방식 | 역할과 한계 |
| --- | --- | --- |
| 1. 추출 | 정답 선택지, 정답 해설, 질문, 목차 제목 순으로 입력해 주장 한 문장과 주요 개념을 구조화 | 서버 내부의 정답 데이터를 사용한다. 모호한 선택지, 사실 확인이 어려운 내용은 제외한다. |
| 2. 후보 검색 | 개념 태그 일치, 한국어 키워드 검색, 문장 임베딩 유사도를 합쳐 가능한 쌍을 좁힘 | 키워드만 쓰면 다른 표현의 같은 생각을 놓치고, 임베딩만 쓰면 대립하는 주장도 가깝게 잡힐 수 있다. 둘 다 확정 판정으로 쓰지 않는다. |
| 3. 관계 판정 | 후보 두 개의 주장·정답 해설·근거를 AI에 주고 유형, 방향, 설명, 신뢰 근거, `연결 안 함`을 구조화해 받음 | AI가 빈 근거를 만들어 채우지 못하게 한다. 원문이 없다면 퀴즈 내용 사이의 관계라고만 판정한다. |
| 4. 검증 | 두 원본 ID 존재, 같은 퀴즈끼리 금지, 양쪽 근거 문장 존재, 관계 유형과 설명의 일치, 중복·상충 관계 확인 | 통과한 관계만 자동 공개한다. 낮은 신뢰도와 검증 실패는 비공개로 두고, 신고가 누적되면 자동 숨김·재판정한다. |
| 5. 노출 | 사용자가 **둘 다 첫 답을 제출한 퀴즈** 사이의 검증된 관계만 노출 | 읽지 않은 책의 핵심 내용과 정답을 지도에서 미리 보여주지 않는다. |

기계적 방법만으로도 `동일 개념 태그`를 묶어 **같은 주제의 퀴즈 목록**은 만들 수 있다. 다만 이를 주장 간 관계선으로 표시할 때는 양쪽 내용이 정말 같은 개념을 다루는지 확인한다. 설명이 가능한 관계를 늘릴 때 AI 판정을 더한다. 벡터 DB나 그래프 DB는 처음부터 필수는 아니다. 퀴즈와 후보 수가 작을 때는 기존 DB의 관계 테이블과 배치 작업으로 시작하고, 후보 검색 규모가 커질 때 임베딩 인덱스를 검토한다.

### AI 판정 입출력의 원칙

입력은 두 퀴즈의 질문, **정답 선택지**, 정답 해설, 목차·책 제목, 각 자료의 근거 수준으로 제한한다. 오답 선택지를 함께 사용한다면 “저자의 주장” 추출 대상에서 제외하고 개념 구분에만 사용한다. 출력은 `relationType`, `fromQuizId`, `toQuizId`, `reason`, `supportA`, `supportB`, `decision`을 요구한다. `decision=NO_LINK`를 정상적인 결과로 취급한다. 연결 이유는 두 지지 문장에 실제로 있는 내용만 사용한다.

## 데이터와 API 초안

다음은 신규 설계안이며, 현재 구현된 계약이 아니다.

```text
QuizConcept(quiz_id, quiz_revision, claim, concept_tags, scope,
            evidence_level, source_ref, status)
ConceptLink(id, quiz_a_id, quiz_b_id, type, direction, reason,
            support_a, support_b, confidence, status, model_version, reviewed_at)
```

- 관계는 `quizId` 쌍의 정렬된 키로 중복을 막되, 방향성은 별도 필드로 저장한다. 퀴즈 수정·재생성 시 그 퀴즈에 닿은 관계를 재검토한다.
- 자동 판정은 주기 배치 또는 퀴즈 생성 완료 이벤트로 수행한다. 사용자 요청 때마다 AI를 호출하지 않는다. 사용자의 풀이 여부는 **조회 시** 적용한다. 여러 사용자가 같은 퀴즈를 풀어도 관계는 재사용된다. 포인트 지급 이력은 사용자별 `quizId`·`linkId`로 중복을 막는다.
- `GET /api/v3/learning/me/reading-map-links?quizIds=...` 같은 조회 API는 서버가 인증 사용자 풀이 기록을 확인한 뒤 양쪽 모두 푼 관계만 반환한다. 클라이언트가 보낸 ID만 믿지 않는다. 정답 요지를 응답할 경우에도 같은 검사를 적용한다.
- 지도에는 기존 계층 선과 의미 연결선을 구분해 전달한다. `type`, `reason`, 양쪽 퀴즈 ID, 품질 상태를 포함하고, 현재 지도처럼 복습 목록을 최대 10페이지까지만 읽는 경우에는 **일부 기록만 표시**한다는 상태를 유지한다. 전체 독서지도라면 서버 쪽 커서 페이지네이션 또는 전용 조회가 필요하다.
- 오류 신고가 누적돼 숨긴 관계는 재판정 전까지 모든 사용자에게 재노출하지 않는다. 사용자별 숨김 기능을 넣는다면 별도 저장한다.

## 출시 순서와 검증

1. **작은 표본 확인:** 이미 생성된 퀴즈에서 질문·정답·해설 50~100개를 살펴본다. “하나의 주장으로 뽑을 수 있는가”, “원문 근거가 있는가”, “연결할 가치가 있는가”를 분류한다. 이는 자동 공개 규칙을 정하기 위한 출시 전 품질 점검이며, 매번 사람이 선을 만드는 운영 과정은 아니다.
2. **좁은 MVP:** 같은 책 안에서, 둘 다 푼 퀴즈 중 태그와 주장 일치 검증을 통과한 `같은 개념` 관계만 자동 공개한다. 화면에는 대표 연결 카드 1~3개와 선택형 오류 피드백을 둔다. 가시적인 연결이 0개인 지도도 정상 상태로 둔다.
3. **관계 유형 확대:** 태그·키워드·임베딩으로 후보를 찾고 AI가 `상호보완`·`대조` 등 관계 유형과 이유를 제안한다. 출시 전 표본 평가로 유형별 자동 공개 기준을 정하고, 기준에 못 미친 후보는 노출하지 않는다.
4. **책 사이 확장:** 책 내부 관계의 오탐이 충분히 낮아진 뒤 다른 책으로 넓힌다. 동일 주제의 반복뿐 아니라 대조 관계가 독자의 이해에 도움이 되는지 별도로 평가한다.

출시 판단은 선의 수보다 **정확도와 이해 효과**로 한다. 평가 표본에는 `연결해야 하는 쌍`, `연결하면 안 되는 쌍`, `대조로 연결해야 하는 쌍`을 모두 넣고, 두 명 이상이 독립적으로 유형과 이유를 판정한다. 공개 후보의 잘못된 연결 비율, 설명 카드 열람 후 “연결 이유를 이해했다” 응답, 연결 카드에서 재복습으로 이어진 비율을 본다. 근거가 빈약한 장르·책은 연결 비율이 낮아도 억지로 채우지 않는다.

## 결정이 필요한 지점

- 책 원문 또는 신뢰할 수 있는 발췌·출판사 자료를 확보할 수 있는가? 없으면 퀴즈 간 의미 관계까지만 주장한다.
- 자동 공개 기준을 유형마다 어떻게 정할지? 처음에는 `같은 개념`만 좁게 공개하고, 표본 평가 결과를 보고 확장한다.
- 연결을 지도 위 선과 카드 중 어떤 비중으로 보여줄지? 모바일에서는 카드의 이해·탐색 지표를 우선하고, 지도는 보조로 둔다.
